# Model card — route-risk-xgb-v1

> **Synthetic data, prototype model.** This model was trained entirely on synthetic data
> generated by the project itself. Its test metrics measure how well XGBoost recovers a known,
> documented relationship. They are **not** evidence of accuracy on real roads in the North
> Eastern Region, and the model has not been validated against any real closure record.

| | |
|---|---|
| **Name / version** | `route-risk-xgb-v1` |
| **Type** | `xgboost.XGBRegressor` (XGBoost 3.4.1), 293 trees |
| **Objective** | Continuous route-risk score, 0–100 (`reg:squarederror`) |
| **Artifact** | `artifacts/route-risk-xgb-v1.json` (SHA-256 `d3b3efd4833cb8f9…`), metadata alongside |
| **Served by** | `ml/app` (FastAPI, internal), called only by Express |
| **Explanations** | SHAP `TreeExplainer`, exact Shapley values, per prediction |

## Intended use

Scoring corridor segments and candidate routes for the SIH prototype, and explaining each score
with its feature contributions. It is a demonstration that the pipeline runs genuine inference —
features → model → score → SHAP → PostgreSQL — not a decision-grade risk model.

**Not intended for** operational routing, safety decisions, or any claim of predictive accuracy.

## Inputs

The twelve features of PROJECT_CONTRACT §5, in this order. `season` was dropped by the contract
review and is rejected if sent.

| Feature | Unit / encoding | Training range |
|---|---|---|
| `rainfall1h` | mm | 0–25 |
| `rainfall3h` | mm | 0–60 |
| `rainfall6h` | mm | 0–95 |
| `rainfall24h` | mm | 0–150 |
| `windSpeedKmh` | km/h | 0–70 |
| `roadCondition` | GOOD = 0, FAIR = 1, POOR = 2 | 0–2 |
| `terrainSlopeDeg` | degrees | 0–40 |
| `elevationM` | metres | 0–4200 |
| `historicalLandslides` | count | 0–15 |
| `historicalFloods` | count | 0–12 |
| `previousClosureFrequencyPct` | % | 0–45 |
| `trafficLevel` | 0 low, 1 medium, 2 high (§1); continuous for route means | 0–2 |

Inputs outside the training range are still scored — a tree ensemble holds its edge value beyond
what it saw — but the response lists them in `warnings`. The heavy-rain scenario's 6-hour
rainfall (100.9 mm) is one such case.

## Training data

- **12,000 rows**, generated deterministically (`numpy.random.default_rng(20241118)`), dataset
  SHA-256 `5ac030607b369b4d…`. Regenerating produces identical bytes.
- Features are **correlated, not independent**: rainfall windows are nested within a storm, wind
  rises with the storm, slope rises with elevation, high roads are more often POOR, landslide
  history follows slope, flood history is higher in valleys, closure frequency follows incident
  history, and traffic is heavier on the plains.
- **Labels** come from the project's documented weighted relationship (`training/label_formula.py`),
  first defined in PROJECT_CONTRACT's ground-truth generator and cited by the frozen demo:

  ```
  weather = 0.45·rain24h + 0.20·rain6h + 0.15·rain3h + 0.10·rain1h + 0.10·wind   (each normalised, clamped)
  road    = roadCondition / 2
  history = 0.45·landslides + 0.30·floods + 0.25·closureFrequency
  terrain = 0.65·slope + 0.35·elevation
  traffic = trafficLevel / 2

  risk  = 0.30·weather + 0.25·road + 0.20·history + 0.15·terrain + 0.10·traffic
  label = clip(100·risk + ε, 0, 100),   ε ~ Normal(0, 2.5)
  ```

  The label depends on all twelve features, several saturate, and the noise means no input maps
  to exactly one output — so the model must learn the weights, not memorise a table. Inference
  code cannot import this module (a test enforces it).

## Split and metrics

Seeded 70 / 15 / 15 split. Validation drives early stopping only; test rows are never seen
during fitting or model selection.

| Split | Rows | MAE | RMSE | R² |
|---|---:|---:|---:|---:|
| Train | 8,400 | 1.908 | 2.375 | 0.969 |
| Validation | 1,800 | 2.092 | 2.606 | 0.962 |
| **Test** | **1,800** | **2.079** | **2.623** | **0.961** |
| *Predict the training mean* | 1,800 | 10.978 | 13.321 | −0.001 |
| *Noiseless formula (irreducible error)* | 1,800 | 1.926 | 2.425 | 0.967 |

**How to read this.** The labels carry Normal(0, 2.5) noise, so no model can get test RMSE much
below ~2.4. Test RMSE of 2.62 means XGBoost recovered nearly all the learnable signal — **of a
function the project wrote.** The small train/test gap indicates no meaningful overfitting.
None of this says anything about real-world performance.

## Hyperparameters

`learning_rate 0.05`, `max_depth 5`, `min_child_weight 3`, `subsample 0.9`,
`colsample_bytree 0.9`, `reg_lambda 1.0`, `tree_method hist`, up to 1,500 trees with
early stopping at 50 rounds (stopped at 293), `random_state 20241118`, `n_jobs 1`.

**Monotone constraints: +1 on every feature.** More rain, a worse road, a steeper slope or a
longer incident history must never make a route *safer*. Without the constraint, a tree ensemble
can learn small inversions from label noise that would surface in SHAP as nonsense ("heavier
rainfall decreases risk"). The constraint restricts the function's shape, never its values.

Training is single-threaded and seeded, so it is byte-reproducible. The training script refuses
to overwrite an existing v1 artifact that differs from a fresh build — a changed model should be
a new version, because every stored prediction carries this version string.

## Explanations (SHAP)

`shap.TreeExplainer` (tree-path-dependent, exact). For each prediction:

1. compute SHAP values for all twelve features;
2. rank by absolute value, keep the top five;
3. `contributionPct = |shap_i| / Σ|shap| over the five × 100` — normalised over the displayed
   factors, so the five sum to 100;
4. keep the real feature value, the signed SHAP value, and a direction
   (`increases_risk` / `decreases_risk`).

Additivity holds and is tested: `shapBaseValue + Σ all SHAP values = raw prediction`.

**Directions are relative to the base value** (~35, the average synthetic corridor), not to zero.
Moderate rainfall is below the training average, so at baseline it appears as *decreases risk* —
correct Shapley semantics, and worth saying out loud when presenting.

No language model produces or alters any number. Gemini (a later phase) may only narrate these
structured factors.

## Known limitations and risks

- **Synthetic ground truth.** The model can be no better than the formula that labelled it, and
  that formula encodes the project's assumptions, not observed closures.
- **CRITICAL is rare.** Scores of 85+ need near-maximal conditions on every axis at once; few
  training rows reach it. The model predicted Route A at 77 (HIGH) under the storm the demo
  rates 87 (CRITICAL).
- **Seed features are imperfect.** Per-segment slopes derived in Phase 4A are mostly 0–3°, so
  mountain segments look like valley roads to the model. See `docs/ML_REGRESSION_5A.md`.
- **Correlated rainfall inputs.** In the database the 3h and 6h totals are fixed multiples of the
  1h value; SHAP will split credit among them somewhat arbitrarily.
- **No calibration or drift monitoring.** Not needed for a prototype; required before anything
  operational.

## Provenance on every prediction

Each response and each persisted `RiskPrediction` row carries `modelVersion`,
`provenance = ML_PREDICTION`, `trainedOn = synthetic`, the dataset and artifact hashes, the exact
twelve inputs, the SHAP base value, and the scenario it was made under.
